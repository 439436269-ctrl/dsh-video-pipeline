# 19 个 skill 撑起一条短视频流水线：编排怎么调度，17 个原子各做什么

**先看成品**：B 站合集已经更到 **EP150**（每个合集 150 集）——[读诗版](https://www.bilibili.com/video/BV1uupE6bEru) · [故事版](https://www.bilibili.com/video/BV18MpE6FEs6)。

我做了一条真实在跑的短视频流水线（唐诗短剧方向），把它拆成了 19 个 skill，现在装进 agent 就能用。

拆法的核心是**分两层**：一层编排，一层原子。

- **1 个编排 skill**：只做调度和确认门，不做具体活
- **17 个原子 skill**：每个只管一个环节——配音、出图、出视频、合成、封面、核验、发布、复盘
- **1 个总入口**：告诉你每个环节该加载哪个原子 skill

这篇主要讲这两层各自是怎么做的，踩坑放在最后一节。

## 一、编排层：一个 skill 只做「调度 + 两道门」

编排 skill 里没有一行 ffmpeg 命令，它管的是**什么时候做什么、什么时候必须停下来问你**。

**两道确认门**是它最核心的东西：

- **门①：报价。** 选题定了之后，先把这一集要花多少钱算出来给你看，你点头才允许调 API。我第一版没有这道门，让 agent 自己判断要不要生图——一次对话就把预算烧穿了。有了门①，成本从「事后看账单」变成「事前可控」。
- **门②：发布确认。** 成片、标题、封面、可见性都摆出来，你确认了才发。发布是不可逆动作，这道门不能省。

**中间还有一道质量门**：成片核验不通过，绝对不允许进发布队列。自动化的风险就在这——一件错的东西能自动发到四个平台。

整条流水线的编排关系是这样的：选题 → 门①报价 → 配音/素材/成片调度 → 质量核验 → 门②发布确认 → 四平台并行 → 回写飞书 → 数据复盘，复盘结果回到最前面修正选片权重。

## 二、编排层真正难写的部分：节奏

功能性的调度（先配音再合成）谁都会写。**值钱的是那些「什么时候不该做」的规则**，它们全是从数据复盘里长出来的：

- **每天 1-2 条、间隔 ≥4 小时、铺满 24 小时窗口。** 禁止在几小时内连发十几条——同质内容会互相抢推荐池，实测会让整体表现一起塌掉。
- **单平台单日 ≤20 条，且单波发完。** 多轮实测的结论很反直觉：**单日条数越多、次日冷启动越差**，超量之后哪怕拆成两波也救不回第二波。
- **主波放在 12:00–15:00，禁 22:00 之后的晚波。** 晚波实测全是地板。
- **进池判定要锚定**平台自己的数据口径，不能拿自己的直觉当标准。

还有一条关于「优化位在哪」的结论也反直觉：**时长不是变量**——AB 两个版本的时长与播放没有明显相关。所以优化位置被固定在两个地方：**前 3 秒的钩子**和**发布节奏**，而不是把片子改长改短。

这些规则写进 skill 之后，agent 每次都会遵守；放在我脑子里的时候，赶进度就会被忘掉。

**还有一个数让我印象很深：一集端到端 59 分钟，真正在生产的时间只有 7 分钟。**

我把某天的时间线还原了一遍（用产物时间和 agent 调度记录反推）：TTS 十条配音 37 秒、六张场景图 2 分钟、一条文生视频 2.3 分钟、九条运镜镜头 25 秒、两版合成 11 秒、抽帧和封面加核验 30 秒——**生产段加起来约 7 分钟，占全部的 12%**。

剩下 88% 花在发布等待和主线程同步上：B站 10 分钟、视频号 11 分钟，而抖音要 **47 分钟**（两个 agent 争用同一个浏览器配置就吃掉 12 分钟，撞车重跑 2.5 分钟，封面传播等待 2 分钟，还有 10 分钟延迟审计空转）。主线程还得等最慢的那个 agent 才回写，**下一集的生产被整段卡住**。

所以编排优化改的是这些：主线程不再等最慢的 agent、把抖音的延迟审计挪出关键路径、多个发布 agent 不共用浏览器配置、文案不内联进 prompt（会触发内容过滤中断）。目标是 **25 分钟一集，质量门一道不减**。

自动化的通病就在这：**你以为瓶颈在生成，其实在等待和同步。**

## 三、编排层的双版本规格

同一条素材线跑两个版本，规格全部定稿写死在 skill 里：

| 版本 | 时长 | 结构 | 硬约束 |
|---|---|---|---|
| A 读诗版 | 25-27 秒 | 题卡 → 四句连读 → 全诗字卡 + 尾钩 | 语速必须用报幕同款自然语速，禁「慢速/朗诵腔」提示词；同一集内相邻配音间隔要统一 |
| B 故事版 | 60-90 秒 | 前 3 秒钩子 → 三幕 → 点诗 → 下集钩子 | **最大静默 ≤3.2 秒**，且必须用 astats 数值核验；旁白/男声/少女三个角色分别固定音色 |

图片运镜和 AI 视频是两条生产路线（前者用 ffmpeg zoompan 把关键帧推成镜头，后者用 Seedance 文生视频），编排 skill 里写清了哪个阶段用哪条、以及切换的时间点。

**成本基线**也写在编排层：把 t2v 从 720p 切到 480p，实测省 53.5%（5 秒镜头 50,638 vs 108,900 tokens），代价是合成时要升采样回 720p——所以规则是「先抽检再全量切」。

## 四、原子层：17 个 skill 各自怎么做

这部分是真正干活的地方。挑几个说：

**配音（读音校正）**。中文古诗文最大的坑是多音字。这个 skill 里有一张同音字替换表（朝 zhāo / 还 huán / 重 chóng / 骑 jì / 教 jiào / 载 zǎi 等），并且提供了三种校验模式：批量修、批量查、以及**逐字拼音校准**——按整句语境给出每个字的读音，对多音字单独标 ⚠ 让人裁决。产出的是「TTS 安全文本」。音色和 context 模板也是分开的：题卡、逐句、尾钩、点诗、旁白各有各的写法，因为同一句话在不同位置该有的语气完全不同。

**画面（三条生成线）**。同一个需求有三条路，skill 里写了一张选路表：配额制的专属通道、按量后付费的标准通道（按张价格差一倍多）、以及第三方画布 CLI 作为备用线。选路的依据是「配额还有没有、要不要批量、质量要求多高」，不是随便挑一个。

**文生视频**。一次生成一条 720p 竖屏镜头：create → poll → download，处理失败重试、任务列表、取消删除，还带一份 token 用量与刊例价格的换算公式——**让「这一条镜头多少钱」可算**。

**合成**。喂一条 manifest JSON（镜头列表 + 配音时间轴 delay_ms + SRT），输出一条竖屏成片：归一化拼接、混音、烧字幕、+faststart。这里有个刻意的设计：**字幕烧录失败会自动降级重试**——宁可少一层字幕，也不能整条片子出不来。

**封面**。一张关键帧 + 系列角标 + 标题 + 诗行，一次输出两个规格（16:10 的横版和竖版），因为不同平台用不同比例，分两次做就容易不一致。

**核验（三件套）**。这是我最喜欢的一个原子 skill：用 astats 做**分窗 RMS 能量核验**（判断配音和静默窗有没有对齐）、用音频互相关（audio-NCC）**把线上视频的音频和参考 wav 比对**（判断平台上那条到底是不是本版文件、有没有错版读音）、以及**抽帧亮度检测**白屏黑屏。它替代了「用眼睛看图」这种不可靠的验收方式。

**发布**。默认**四个平台各起一个 agent 并行发**，主 agent 只做确认门、文案变体和进度回写。每个平台有各自的底层工具（B 站走 biliup 凭据、视频号走官方引擎、抖音走创作者中心注入、小红书走 CDP）。发布完要**收回链接**，写回飞书多维表格。合集管理也在这里：创建合集、批量加单集、排序、验证。

**复盘**。三平台数据回收 → 按**龄期衰减分档**（新发的和发了几天的不能直接比）→ A/B 与题材对照 → 发布节奏实验裁决 → **反过来修正选片权重**。这就是闭环：复盘结果会改掉编排层的选片标准，下一批的选题逻辑随之改变。

## 五、为什么值得这么拆

三个理由：

1. **原子能力可以单独用。** 我只想给一句话配音，不需要读整个流水线。
2. **编排能改，原子不用动。** 发布节奏我改了十几次，合成脚本一行没碰。
3. **判断被固化了。** 什么时候该停、一批发几条、什么情况不许发——这些东西原本在我脑子里，写下来才真的可复用。

## 六、踩坑（就这一节）

发布前我给这套东西加了一道隐私门，因为我原以为「skill 里能有什么隐私」——**这个判断是错的**。扫出来一枚 46 字符的真 API key、硬编码的作品 ID、平台签名 URL、以及 175 个只该留在我本机的文件（真实数据快照、逐集一次性脚本、操作截图）。

所以我没有手改，而是写了一个可复现的导入器：剔除规则、脱敏规则、残留扫描规则写在同一个文件里，每次发布前跑一遍。最后剔除 175 个文件、脱敏 35 个、残留 0。

更有意思的是**这道门抓住了我自己 5 次**，包括一次「脱敏规则把源码里的解析正则改坏了」——于是我给门加了一关：所有脚本逐个做语法解析。

还有一条教训值得单独说：**一条通过的断言，不代表它会咬人。** 我新加了一条「包内文档必须与最后一次提交一致」的检查，写完顺手做了个反向测试——故意改一个字节，它**照样通过**。原因很蠢：打包本来就取自工作区，我却拿包内文档跟工作区比。改成跟 git 提交比之后才真的会失败。

现在的规矩是：每加一条检查，先试着让它失败一次。

## 七、怎么用

```sh
# DSH 插件（19 个 skill 一起装进去）
dsh plugin --profile web add dsh-video-pipeline

# Claude Code / Codex（同一套 skill 的宿主中立版）
claude plugin marketplace add 439436269-ctrl/video-pipeline-skills
claude plugin install video-pipeline@video-pipeline-skills
```

需要自己准备：**ffmpeg**、**Python 3 + Pillow**、**Node.js**，以及各平台自己的登录凭据。**这套东西不含任何凭据。**

- 仓库：[dsh-video-pipeline](https://github.com/439436269-ctrl/dsh-video-pipeline)
- 宿主中立版：[video-pipeline-skills](https://github.com/439436269-ctrl/video-pipeline-skills)
- npm：[dsh-video-pipeline](https://www.npmjs.com/package/dsh-video-pipeline)

流水线的价值不在「自动化」，在于它把流程里的判断留下来了。如果你也在做类似的事，欢迎交流。
