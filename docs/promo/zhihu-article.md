# 一条短视频流水线拆成 19 个 skill：编排怎么做，17 个原子各做什么

**先看成品**：B 站合集已经更到 **EP150**（每个合集 150 集）——[读诗版](https://www.bilibili.com/video/BV1uupE6bEru) · [故事版](https://www.bilibili.com/video/BV18MpE6FEs6)。下面这套东西就是它背后的生产系统。

一条真实在跑的短视频生产流水线（唐诗短剧方向），拆成 **19 个 skill**：1 个总入口 + 1 个编排 + 17 个原子能力。已发布成 DSH 插件，同时有一份宿主中立版给 Claude Code / Codex。

## 先说结论：它值不值得装

如果只给一条理由：**它把「编排」装进了技能目录，而不只是堆一堆提示词**——技能目录里从此有一条会自己按节奏推进、到关键处必须停下来问你的生产线。

- **19 个 skill 一次装齐**：1 总入口 + 1 编排 + 17 原子，装完直接出现在技能目录，不需要往 `~/.agents/skills` 复制任何文件
- **零运行时依赖**：`dependencies` 与 `peerDependencies` 都是空的，不存在「版本组合装不上」这类问题
- **不抢你自己的 skill**：内置 skill 优先级最低，你本地已有同名 skill 时以你的为准，不会被悄悄覆盖
- **发布前过机器隐私门**：剔除 175 个文件、脱敏 35 个、残留 0（为什么必须这么做，见第七节）
- **同一套 skill 也能装进 Claude Code / Codex**：不用 DSH 也能用（宿主中立版单独一个仓）
- **它是一条真在跑的产线**：B 站两个合集各更到 150 集，不是 demo

下面是它内部怎么运转的：编排层怎么调度，17 个原子各做什么。

这篇主要讲两层各自怎么做的：**编排层怎么调度、原子层各自怎么实现**。踩坑放在最后一节。

## 一、分层：编排只做判断，原子只做能力

| 层 | 数量 | 职责 |
|---|---|---|
| 总入口 | 1 | 环节与原子 skill 对照、占位符、前置依赖 |
| 编排 | 1 | 选题 → 门①报价 → 生产调度 → 质量核验 → 门②发布确认 → 并行发布 → 回写 |
| 原子 | 17 | 配音 / 出图 / 出视频 / 运镜 / 合成 / 封面 / 核验 / 复盘 / 发布 / 回写 |

拆开之后有三个直接收益：原子能力可以单独复用（只想给一句话配音，不必读整条流水线）；编排改发布时间不用碰合成脚本；编排层不引用一堆 API 细节，上下文占用小。

素材生产还有两条并行路线：**路线①图片运镜**（ffmpeg zoompan 把关键帧推成镜头）与**路线② Seedance 文生视频**（t2v 直接出动态镜头）。编排 skill 里写明了哪个阶段用哪条、以及切换的时间点。

## 二、编排层：三道门

编排 skill 里没有一行 ffmpeg 命令。它管的是「什么时候做什么、什么时候必须停下来问人」。核心是三道门：

**门①报价。** 选题定了先算这一集要花多少钱，人点头才允许调 API。我第一版没有这道门，让 agent 自己判断要不要生图——一次对话把预算烧穿了。有了门①，成本从「事后看账单」变成「事前可控」。

**质量门。** 成片核验不通过，绝对不允许进发布队列。自动化的真正风险不是「发不出去」，而是**一件错的东西能自动发到四个平台**。

**门②发布确认。** 成片、标题、封面、可见性摆出来，人确认才发。发布不可逆，这道门不能省。

## 三、编排层最值钱的部分：节奏与产能

功能性调度（先配音再合成）谁都会写。**真正值钱的是「什么时候不该做」的规则**，它们全部来自数据复盘：

- **每天 1-2 条、间隔 ≥4 小时、铺满 24 小时窗口。** 禁止几小时内连发十几条——同质内容互相抢推荐池，实测会让整体表现一起塌。
- **单平台单日 ≤20 条，且单波发完。** 多轮实测的结论反直觉：**单日条数越多、次日冷启动越差**；超量之后哪怕拆成两波也救不回第二波。
- **主波 12:00–15:00，禁 22:00 后的晚波**（晚波实测全地板）。
- **进池判定必须锚定平台自己的数据口径**，不能拿直觉当标准。

另一条反直觉的结论是**时长不是变量**：AB 两版的时长与播放没有明显相关。所以优化位被固定在两处——**前 3 秒钩子**与**发布节奏**，而不是把片子改长改短。

还有一条平台差异：视频号的描述**首行要带名句**，因为这个平台的搜索权重值得单独优化。

## 四、编排层：双版本规格与成本基线

同一批素材跑两个版本，规格定稿写死在编排 skill 里：

| 版本 | 时长 | 结构 | 硬约束 |
|---|---|---|---|
| A 读诗版 | 25-27 秒 | 题卡 → 四句连读 → 全诗字卡 + 尾钩 | 语速用报幕同款自然语速，禁「慢速/朗诵腔」提示词；同集内相邻配音间隔统一 |
| B 故事版 | 60-90 秒 | 前 3 秒钩子 → 三幕 → 点诗 → 下集钩子 | **最大静默 ≤3.2 秒**，且必须 astats 数值核验；旁白/男声/少女固定三个音色 |

**标准时序 ≤25 分钟/集，质量门全保留**——这是多轮实测后定的编排目标：可以快，但不能为了快跳过门。

**成本基线**也写在编排层：t2v 从 720p 切到 480p 实测省 53.5%（5 秒镜头 50,638 vs 108,900 tokens，刊例 ¥1.16 vs 2.50），代价是合成时要升采样回 720p。所以规则不是「一律用 480p」，而是**先抽检再全量切**。

选片权重同样在编排层，而且会被复盘改写：样片诗单的五条标准按前 20 集数据重排了权重，选新集前必读。

### 一集 59 分钟，真正在生产的时间只有 7 分钟

我把某一天的时间线还原了一遍（用产物 mtime + agent 调度记录反推）：

| 阶段 | 耗时 |
|---|---|
| TTS 10 条配音 | 37s |
| 场景图 ×6（串行） | 2.0min |
| t2v ×1（create→poll→download 串行） | 2.3min |
| zoompan 镜头 ×9 | 25s |
| manifest + 合成 A/B 两版 | 11s |
| 抽帧 + 双平台封面 ×4 + astats 核验 | ~30s |

生产段合计约 **7 分钟**，端到端却要 **59 分钟**——**88% 的时间花在发布等待和主线程同步 `wait` 上**。

发布段里 B站 10.2 分钟、视频号 10.8 分钟，而抖音 **47.4 分钟**：其中 12 分钟是两个 agent 争用同一个浏览器 profile，2.5 分钟是撞车重跑，2 分钟是封面传播等待，还有 10.3 分钟是延迟审计空转。更糟的是主线程必须 `wait` 最慢的那个 agent 才回写，**后一集的生产被整段阻塞**（跨集甚至出现过 105 分钟空转）。

对应的编排修改，每一条都很具体：

- 主线程不再 `wait` 最慢的 agent，下一集生产不再被阻塞
- 抖音的「15 分钟延迟审计」移出关键路径
- 多个发布 agent 不共用浏览器 profile（会互相杀进程）
- 文案不内联进 spawn 的 prompt（会触发内容过滤中断），改外置文件
- 收敛 `create→poll` 串行与主线程十几次工具往返

优化目标是 **≤25 分钟/集，且质量门一道不减**。这其实是自动化的通病：**你以为瓶颈在生成，其实在等待和同步**。

## 五、原子层：17 个 skill 各自怎么实现

### 配音

中文古诗文最大的坑是**多音字**。这个 skill 做三件事：

1. 一张同音字替换表（朝 zhāo / 还 huán / 重 chóng / 骑 jì / 教 jiào / 载 zǎi 等）。
2. `pinyin_fix` 三种模式：**fix**（批量修）、**check**（批量查）、**pinyin**（逐字拼音校准——按整句语境给每个字的读音，多音字单独标 ⚠ 让人裁决）。
3. 产出「TTS 安全文本」，保证送进 TTS 的是已经消歧过的文本。

音色与 context 模板也分开维护：题卡、逐句、尾钩、点诗、旁白各一套写法。同一句话在不同位置该有的语气完全不同，用一套模板必然出错。

### 画面：三条生成线要选

同一个需求有三条路，skill 里有一张选路表：

- **配额制专属通道**（Agent Plan）：有配额时优先，专属端点、尺寸规则与配额计费单独一套。
- **标准按量通道**：按张后付费，按张价格差一倍多（pro / flash / lite 不同价），配额用尽时切过来。
- **第三方画布 CLI**：备用生成线。

选路依据是「配额还有没有、要不要批量、质量要求多高」，而不是随手挑一个。

### 文生视频与图片运镜

- **t2v**：一次生成一条 720p 竖屏镜头，create → poll → download，含失败重试、任务列表、取消删除，以及一份 **token 用量与刊例价格的换算公式**——「这一条镜头多少钱」是可算的。
- **图片运镜**：单张关键帧用 ffmpeg zoompan 出竖屏 720×1280 镜头，支持缓推/缓拉、可调秒数/帧率/变焦幅度，批量由外层循环调用。

### 合成

喂一条 **manifest JSON**（镜头 mp4 列表 + 配音 wav 时间轴 `delay_ms` + SRT 字幕），输出一条竖屏成片：归一化拼接、`adelay`/`amix` 混音、烧字幕、`+faststart`。

一个刻意的设计：**字幕烧录失败会自动降级重试**。宁可少一层字幕，也不能整条片子出不来——批量生产里，一个环节的硬失败会拖垮整晚的排产。

### 封面

一张关键帧 + 系列角标 + 标题 + 诗行，**一次输出两个规格**：16:10 横版（1146×717）与竖版（1080×1920）。不同平台用不同比例，分两次做必然不一致。

### 核验：三件套

这是我最喜欢的一个原子 skill，因为它把「验收」从肉眼看图变成了数值：

1. **astats 分窗 RMS 能量核验**：判断配音与静默窗有没有对齐（也是 B 版「最大静默 ≤3.2 秒」的执行者）。
2. **audio-NCC 线上比对**：把平台上那条视频的音频和本地参考 wav 做互相关，判断**线上到底是不是本版文件**、有没有错版读音。
3. **抽帧亮度检测**：白屏/黑屏自动发现。

第 2 条解决的是一个很实际的问题：视频发出去之后，你怎么知道平台上跑的确实是你这一版？

### 发布

- **四平台并行**：默认**每个平台起一个 agent**，主 agent 只负责确认门、文案变体准备与进度回写。
- **各平台底层工具**：B 站走 biliup 凭据与投稿、视频号走官方引擎的命令、抖音走创作者中心上传注入、小红书走 CDP 管线。
- **合集管理**：创建合集、批量加单集、排序、验证——都做成了可复用命令，不是每次手点。
- **收尾**：发布后收回链接，写回飞书多维表格。
- 另有一个「按 JSON 配置顺序批量发布」的编排器，覆盖七个平台，兼容三个操作系统。

### 复盘（闭环的起点）

三平台数据回收 → **按龄期衰减分档**（刚发的和发了三天的不能直接比）→ A/B 与题材对照 → 发布节奏实验裁决 → **反过来修正选片权重**。

这一步是整个系统的闭环：复盘结论会改掉编排层的选片标准和节奏规则，下一批的选题逻辑随之变化。**编排层因此不是静态配置，而是会被数据更新的活规则。**

### 回写

用官方 CLI 操作飞书多维表格：解析表格链接、查表/字段/记录、批量增删改。进度以表格为准，不在 skill 里重复维护——避免两处数据打架。

## 六、分层带来的三个好处

1. **可复用**：原子 skill 单独可用。
2. **可演进**：编排改节奏，原子不动；原子换实现，编排不动。
3. **可交接**：判断被写下来了。什么时候该停、一批发几条、什么情况不许发——原本在人脑子里，写下来才真的能复用，也才能被 agent 稳定执行。

## 七、隐私门与验证（踩坑就这一节）

我原以为「skill 里能有什么隐私」，**这个判断是错的**。发布前扫出来：

- 一枚 **46 字符的真 API key**
- 硬编码的作品 ID、整张集号映射表、平台 UID
- 个人绝对路径、内网地址、带时效签名的平台 URL
- **175 个只该留在我本机的文件**：真实数据快照、合集映射、逐集一次性脚本、操作截图

所以没手改，而是写了一个**可复现导入器**：剔除规则、脱敏规则、残留扫描规则全在一个文件里，发布前跑一遍机器门。结果：剔除 175 个文件、脱敏 35 个、准确性改写 15 处、**残留 0**，并且**所有脚本逐个做语法解析**。

**这道门抓住了我自己 5 次**，包括一次「脱敏规则把源码里的解析正则改坏了」——正是那次之后加的语法解析关。还有一次脱敏让 Python 里的表 ID 变成非法变量名，也是被语法关拦下的。

最值得说的一条教训：**一条通过的断言，不代表它会咬人。**

我新加了一条「包内文档必须与最后一次提交一致」的检查，写完顺手做反向测试——故意改一个字节，它**照样通过**。原因是打包本来就取自工作区，我却拿包内文档跟工作区比，这个断言在数学上不可能失败。改成跟 `git HEAD` 比之后：

```
反向（README 有未提交改动） → exit 1  ❌ 与最后一次提交不一致
正常                        → exit 0  ✅ 逐字节一致
```

同类问题还有两个：`if (!bad.length)` 判的是函数的参数个数（恒为 1），那行确认永远不打印；PowerShell 写 JSON 带的 BOM 会让清单解析失败，而 `claude plugin validate` 只给 warning、**退出码仍是 0**。

现在的规矩：**每加一条检查，先试着让它失败一次。**

## 八、怎么用

```sh
# DSH 插件（19 个 skill 一起）
dsh plugin --profile web add dsh-video-pipeline

# Claude Code / Codex（同一套 skill，宿主中立版）
claude plugin marketplace add 439436269-ctrl/video-pipeline-skills
claude plugin install video-pipeline@video-pipeline-skills
```

前置依赖：**ffmpeg**、**Python 3 + Pillow**、**Node.js**，以及各平台自己的登录凭据。两个仓都**不含任何凭据**——上面那一节就是为此存在的。
